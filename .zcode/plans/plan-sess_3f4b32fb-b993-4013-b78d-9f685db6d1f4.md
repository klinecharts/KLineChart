# План: Быстрые победы по производительности (3 изолированные оптимизации)

Три независимые, локальные оптимизации с высоким ROI и низким риском. Каждая изолирована в одном-двух файлах, не меняет публичное API и не требует архитектурных изменений. Верификация — `pnpm code-lint` + `pnpm type-check` + ручная проверка через `debug/` (тестов в проекте нет).

## Оптимизация 1: Быстрый путь в `formatValue` (самый высокий ROI)

**Файл:** `src/common/utils/format.ts:29-51`

**Проблема:** Каждый вызов `formatValue` парсит ключ через `key.replace(rePropName, callback)` — regex-вызов + аллокация массива `path[]` + замыкание. Самый горячий путь: `eachFigures` (`src/component/Indicator.ts:254-263`) вызывает `formatValue` 4 раза (с простыми ключами `'texts'`, `'circles'`, `'bars'`, `'lines'`) на **каждый видимый бар × каждый индикатор** при каждой перерисовке. При ~300 баpaх × 3 индикатора × 4 = ~3600 regex-вызовов на кадр при pan/zoom.

**Решение:** Добавить быстрый путь для простых ключей (без `.` и `[`) — прямой доступ к свойству объекта, минуя regex. Составные ключи (`'ohlc.upColor'`, `'bars[0].upColor'`, `'circles[0].upColor'`) идут по существующему regex-пути без изменений.

```ts
export function formatValue(data, key, defaultValue?) {
  // быстрый путь: простой ключ без '.' и '['
  if (key.length > 0 && key.indexOf('.') === -1 && key.indexOf('[') === -1) {
    const value = (data as Record<string, unknown>)?.[key]
    if (value !== undefined) return value
    return defaultValue
  }
  // существующий медленный путь с regex — без изменений
  const path: string[] = []
  key.replace(rePropName, ...)
  ...
}
```

**Покрытие быстрого пути:** все 4 вызова в `eachFigures` (основной горячий путь), `'timestamp'` в `Store.ts:638`. Составные ключи (индикаторы volume/macd/sar/ao, ohlc.*) остаются на regex-пути — но они вызываются либо раз на indicator (`getCandleBarOptions`), либо в `indicator.calc` (не в per-frame отрисовке).

**Риск:** Минимальный. Поведение идентично для простых ключей: прямой доступ через `[key]` даёт тот же результат, что и regex-парсинг одноуровневого пути. Проверка `value !== undefined` сохраняет существующую семантику возврата `defaultValue`.

## Оптимизация 2: Кэш разобранных команд path-фигуры

**Файл:** `src/extension/figure/path.ts:117-140`

**Проблема:** Каждый раз при отрисовке path-фигуры строка SVG-пути (`'M0 0L10 10...'`) перепарсивается: `path.match(/[MLHVCSQTAZ][^MLHVCSQTAZ]*/gi)` + для каждой команды `.slice(1).trim().split(/[\s,]+/).map(Number)`. Строки статичны (иконки в стилях, не меняются между кадрами), но парсятся заново на каждой перерисовке. Используется в `CrosshairFeatureView.ts:149-157` и `IndicatorTooltipView.ts:214-222` (иконки фич кросхейра/тултипа) — рисуются при каждом движении мыши.

**Решение:** Module-level `Map<string, Array<{ type: string, args: number[] }>>` — разобрать строку один раз, переиспользовать разобранные команды. Offset (`offsetX`/`offsetY`) применяется при рисовании, как и раньше — в кэше хранятся только `type` + `args` (без offset).

```ts
interface ParsedPathCommand { type: string, args: number[] }
const pathCommandsCache = new Map<string, ParsedPathCommand[]>()

function parsePath(path: string): ParsedPathCommand[] {
  const cached = pathCommandsCache.get(path)
  if (cached !== undefined) return cached
  const commands = path.match(/[MLHVCSQTAZ][^MLHVCSQTAZ]*/gi)
  const parsed: ParsedPathCommand[] = []
  if (commands !== null) {
    commands.forEach((command) => {
      parsed.push({
        type: command[0],
        args: command.slice(1).trim().split(/[\s,]+/).map(Number)
      })
    })
  }
  pathCommandsCache.set(path, parsed)
  return parsed
}
```

В `drawPath` заменить строки 124-140 на чтение из кэша через `parsePath(path)`, оставив switch-логику рисования (строки 141-245) без изменений.

**Риск:** Минимальный. Строки path статичны и иммутабельны после задания в стилях. Кэш растёт без очистки, но bounded количеством уникальных path-строк (десятки в типичном использовании) — памяти пренебрежимо мало. Существующая логика рисования (включая её особенности с `currentX`/`currentY`) сохраняется byte-for-byte.

## Оптимизация 3: Кэш `getBoundingClientRect` в EventHandler

**Файл:** `src/common/EventHandler.ts:858-878` (также затронет `_startPinch` строка 783)

**Проблема:** `_makeCompatEvent` вызывает `this._target.getBoundingClientRect()` на **каждое** событие мыши/тача (mousemove, touchmove, mousedown и т.д.). На hi-DPI трекпадах это 120+ событий/сек. `getBoundingClientRect()` форсирует синхронный layout-рефлоу браузера ("layout thrashing"). EventHandler инстанцируется один раз на чарт (`Event.ts:189`), `_target` — весь `_chartContainer`.

**Решение:** Кэшировать rect в поле `_boundingRectCache`, инвалидировать его на:
1. **mouseEnter** (`_mouseEnterHandler:220`) — пере-чтение в начале hover-сессии (mousemove уже пере-регистрируется здесь, так что это естественная точка).
2. **scroll** — passive listener на `window` (позиция контейнера в окне меняется при прокрутке страницы; координаты `clientX - box.left` требуют актуального `box.left`).
3. **resize** — `ResizeObserver` на `_target` (размеры меняются при изменении layout окна/контейнера).

Добавить приватный метод `_readBoundingRect()` (читает с кэшем) и `_invalidateBoundingRect()` (сбрасывает кэш в `null`). В `destroy()` снимать scroll/ResizeObserver слушатели.

**Риск:** Средний (выше первых двух). Требует аккуратной инвалидации. Чтобы минимизировать риск:
- Passive scroll listener (`{ passive: true }`) — не блокирует прокрутку, дёшев.
- ResizeObserver на `_target` — стандартный паттерн (в Chart.ts уже есть на этом же элементе).
- Инвалидация на mouseEnter покрывает основной интерактивный случай (drag/zoom/crosshair — всё в рамках одной hover-сессии).
- Если по какой-то причине кэш устареет (крайний случай), следующий mouseEnter обновит его.

## Порядок выполнения и верификация

1. **Оптимизация 1** (`formatValue`) — первой, наибольший ROI при наименьшем риске.
2. **Оптимизация 2** (path cache) — второй, изолирована в одном файле.
3. **Оптимизация 3** (`getBoundingClientRect` cache) — третьей, самый аккуратный подход.

После каждой: `pnpm code-lint` + `pnpm type-check`. После всех трёх: запуск `pnpm debug` и ручная проверка — движение кросхейра, zoom колесом, pan drag, pinch на тач-устройстве, прокрутка страницы, resize окна. Убедиться, что координаты кросхейра следуют за курсором точно, тултипы корректны, path-иконки кросхейра/тултипа рисуются правильно.

## Чего НЕ делаем в рамках этой задачи
- Пул Figure-объектов (п.1 общего списка ROI) — крупное архитектурное изменение, отдельная задача.
- Инкрементальный расчёт индикаторов (п.2) — отдельная задача.
- Любые изменения публичного API.
- Добавление тест-фреймворка (отдельная задача; здесь полагаемся на ручную проверку).
